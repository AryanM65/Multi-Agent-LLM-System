# Dataset Preparation — Every Step, In Detail

> How the labeled fault-localization dataset was actually built, from raw pipeline design through to the final verified `dataset/trials.jsonl`. Every mechanism described here is taken directly from the project's code (`btp-pipeline/src/`, `btp-pipeline/scripts/`) and verified generation logs, not from a plan document. Written 2026-09-30.

---

## Step 0 — Decide what one "trial" actually is

A **trial** = one execution of one multi-agent pipeline topology, on one question, with (optionally) one fault deliberately injected at one node. Each trial produces:
- the raw text each node generated (k repeated samples per node)
- a measured uncertainty score per node (how much those k samples disagreed)
- the exact, known ground truth: which node was faulted (if any) and what kind of fault it was

Because the fault is injected deliberately by the generation code itself, the ground truth is **known with certainty** — it never depends on a human labeler's judgment or an external model's guess.

---

## Step 1 — Design the pipeline structure (arbitrary topologies, not just one fixed chain)

**File**: `btp-pipeline/src/topology.py`.

A pipeline is represented as:
```python
NodeSpec(node_id: str, role: str, instruction: str)     # role: "retriever" | "reasoner" | "writer"
Topology(nodes: Dict[str, NodeSpec], edges: List[Tuple[str, str]], topology_id: str)
```

Every topology, before it can ever be used, is run through `validate_topology()`, which enforces 5 rules:
1. Every node has one of the 3 valid roles.
2. Every edge's endpoints reference real node IDs in this topology.
3. **Role ordering is non-decreasing along every edge** — a retriever can feed a reasoner or a writer; a reasoner can feed a reasoner or a writer; a writer can never feed anything (`ROLE_RANK = {retriever: 0, reasoner: 1, writer: 2}`). This encodes the real information-flow constraint of the system being modeled: evidence gets gathered first, reasoned about second, written up last.
4. **The graph is acyclic** — checked by attempting a topological sort (Kahn's algorithm); a cycle raises an error immediately rather than being silently allowed.
5. No node in a multi-node topology is completely isolated (no edges at all).

This validation step is why the pipeline executor can safely assume, everywhere downstream, that any topology it's handed is well-formed — no defensive re-checking needed in the execution or fault-injection code.

### 1.1 The actual topology pool used

Generated by `dataset/generate_topology_pool.py`, saved to `dataset/topology_pool.json`: **20 topologies total**.

- **14 "train" topologies** (3–6 nodes): `chain`, `dual_retriever_fanin`, `triple_retriever_fanin`, `dual_retriever_fanin_deep`, `parallel_reasoner`, `triple_parallel_reasoner`, `crossed_fanin_fanout`, `deep_chain`, `deep_chain_5node`, `star`, `tree`, `wide_fanin`, `wide_fanout_reasoner`, `mixed_asymmetric` — deliberately varied shapes (chains, multiple retrievers feeding one reasoner, one reasoner feeding multiple downstream nodes, deep sequential chains, etc.) so a model trained on them can't just memorize one fixed graph shape.
- **6 "ood_test" topologies** (`ood_random_0` through `ood_random_5`, 5–7 nodes): generated by a **role-before-edges random construction** (assign each node a valid role first, then wire up edges respecting the role-ordering rule — this makes every randomly generated graph valid by construction, no trial-and-error rejection sampling needed). These are **held out completely** — never touched during training or any hyperparameter tuning, used only once, at the very end, to test whether a model actually generalizes to graph shapes it has never seen versus merely memorizing the 14 training shapes.

Each topology entry also carries the exact instruction text sent to every node of each role (its "system prompt," effectively) — e.g. the Retriever's instruction asks it to return only the relevant sentences from the given context; the Reasoner's instruction asks it to think step by step and end with a `FINAL ANSWER:` line; the Writer's instruction asks for a short final answer.

## Step 2 — Choose the question source and build the question pool

**Source**: HotpotQA, the **distractor setting** of the validation split (real multi-hop question-answering data — each question comes with a gold context (the actual supporting evidence) plus additional distractor paragraphs).

**File**: `btp-pipeline/scripts/download_data.py` caches this dataset locally once (~50MB), and `btp-pipeline/scripts/sample_examples.py` builds the actual working pool of questions used for generation:

1. Start from an existing pool of questions (kept for continuity with earlier pilot runs).
2. Randomly shuffle the full cached HotpotQA index (seeded, for reproducibility).
3. Walk through it, and for each candidate question, apply a **quality filter** before accepting it:
   - Must not already be in the existing pool (guarantees no duplicate questions).
   - The question's gold supporting-fact titles must actually be a subset of the titles present in its context (otherwise `get_gold_context()` — the function that extracts the "clean" context for a trial — would fail or return incomplete evidence).
   - Total context length (summed sentence count across all paragraphs) capped at 60 sentences, to keep generation cost and time predictable per trial.
4. Stop once the requested number of new, qualifying questions has been collected; combine with the existing pool and write out.

This is how the question pool was scaled up over the project's history (an original 15-question pilot set → 30 → 60+30 disjoint sets for the larger expansion), always by adding genuinely new questions via this exact filtered-sampling process, never by reusing or duplicating existing ones.

## Step 3 — Self-consistency sampling (how "uncertainty" is actually measured)

**File**: `btp-pipeline/src/nodes.py`.

Every node, every time it runs in a trial, is sampled **k times independently**, at the same temperature (default `0.7`), producing k separate raw text outputs for that one node in that one trial. This is the raw material every uncertainty metric is computed from — nothing else.

The k samples are collected identically regardless of which inference backend is generating them (Ollama, MLX, or vLLM — see Step 7) — the sampling and uncertainty-computation logic is fully backend-agnostic, so switching backends never changes how uncertainty is defined or measured, only how the raw text gets generated.

From those k raw samples, **three complementary uncertainty metrics** are computed (full formulas and worked examples in `docs/feature-engineering-and-processing.md` — summarized here):

| Metric | What it measures | Computed for |
|---|---|---|
| **Lexical uncertainty** | `1 − (fraction of the k samples matching the modal exact-match answer, after normalization)` | Every node, always |
| **Semantic uncertainty** | Embed each of the k samples, greedily cluster by meaning-similarity, then normalized entropy of the resulting cluster-size distribution — "did the *meaning* agree, even if the wording didn't" | Reasoner, Writer only |
| **Jaccard uncertainty** | `1 − mean pairwise set-overlap` across the k samples' parsed item sets | Retriever only, and only when its output splits into multiple discrete items |

**A critical design rule, enforced everywhere in the codebase**: these three numbers are **never merged into one scalar**. `PipelineTrace.uncertainties()` always returns one value per node, `Dict[node_id, float]`. This is the entire reason a graph-structured downstream model makes sense at all — collapsing per-node signal into a single number would throw away exactly the information needed to say *which* node was the problem.

## Step 4 — Design the fault taxonomy and injection mechanics

**File**: `btp-pipeline/src/faults.py`.

Three fault types were designed, each modeling a genuinely different real-world failure mode, and each can be targeted at **any node** in **any topology**:

### 4.1 `noise` — transient instability
**Mechanism**: raise the sampling temperature at the targeted node only, from the default `0.7` to `1.2` (`NOISE_TEMPERATURE`). The node's input is left completely unchanged — only its own randomness is cranked up. Models the idea of "the model just happened to be unstable this time," a fault that should, in principle, be recoverable by simply re-running the same node again.

### 4.2 `contamination` — corrupted input
**Mechanism**: replace the targeted node's actual input with something plausible-but-wrong:
- If the targeted node is a **Retriever**: swap its gold supporting-context paragraphs for ranked *distractor* paragraphs (the same HotpotQA question comes bundled with these — genuinely related-looking but wrong evidence).
- If the targeted node is a **Reasoner or Writer**: replace its parent's real output with a plausible wrong answer drawn from a **substitute bank** — a pool of wrong-but-plausible answers built from other questions' answers, with the clean, correct value explicitly **excluded** from the substitute bank before sampling (so the "wrong" substitute can never accidentally equal the actual correct value — this exclusion was itself a real bug found and fixed, see Step 8).

Models "this agent was fed the wrong information," a fault that should be recoverable by giving the node its correct input back on retry, but *not* by simply retrying with the same (still-wrong) input.

### 4.3 `ceiling` — genuine capability limit
**Mechanism**: strip or harden the targeted node's evidence/instructions to force real information loss:
- **Retriever**: sentences are removed from its context, with a **mandatory verification step** — the correct gold answer string must no longer be findable in the stripped context, or the fault injection is rejected outright (see Step 4.4).
- **Reasoner/Writer**: the node's instruction is *hardened* — e.g. capping the Reasoner to very few reasoning steps, or capping the Writer to a strict word limit (as few as 5 words) — deliberately forcing it to lose information it would otherwise have room to express.

Models a genuine capability gap: even with the same, uncorrupted, un-noised input, the task has been made too hard for the node's own generation budget or evidence access. This should **not** recover on either a same-input retry or a clean-input retry — that's the diagnostic signature that separates it from the other two fault types.

### 4.4 Mandatory verification, and the "never mislabel" rule
`inject_ceiling()` explicitly checks whether the correct answer still survives inside the stripped context. If it does, the function returns `None` — meaning the caller **must** log this as a skip (with a specific reason) rather than silently proceeding with a fault that wouldn't actually be a fault. This same "return `None`, caller must skip and log, never proceed with an invalid injection" pattern is used for every fault type's edge cases (e.g. contamination with an empty substitute bank, or a target node that doesn't exist in a given topology).

### 4.5 Reproducibility
Every fault injector draws its randomness from `make_rng(question_id, fault_type, target_node)` — a dedicated, deterministically-seeded random generator per exact `(question, fault type, target node)` combination — and **never** from Python's global `random` module. This guarantees that re-running the exact same trial specification produces byte-identical corrupted input every time, which matters both for debugging and for the `--resume` crash-recovery mechanism (Step 9).

## Step 5 — Establish a per-question clean baseline first

Before any fault trial runs for a given question on a given topology, a **clean control trial** (`fault_config=None`) is always run first, at every node, with no fault active at all. Its per-node uncertainty values become that specific question's baseline — every subsequent fault trial on that same question is later compared back against this baseline (Step 6) to confirm the injected fault actually produced a measurable effect, not just assumed to have worked.

---

## Step 6 — Verify a fault actually did something (don't just trust the intent)

**File**: `btp-pipeline/src/diagnose.py`, function `verify_against_baseline`.

For every fault trial, once generation completes, the targeted node's observed uncertainty is compared against that same question's clean-control baseline via a **z-score**:
```
z = (observed_uncertainty − baseline_uncertainty) / assumed_std
target_deviated = |z| >= z_thresh   (assumed_std=0.10, z_thresh=1.0, in the k=5-era generation)
```
This produces a `verification` field on every fault trial recording `{target_deviated, z_score, observed, baseline}`. Crucially: **`true_label` is still set from injection intent regardless of whether `target_deviated` came out true or false** — a fault that was genuinely injected but happened not to produce a measurable deviation is still logged as that fault type (this is itself a useful, honest signal — a "hard to detect" case — not something to silently discard or relabel).

A separate, **not used for ground truth**, retry-then-reprobe diagnostic heuristic also exists (`diagnose_trace()`) — it *guesses* a fault type purely from observed uncertainty *patterns* (same-input retry recovers → guess noise; clean-input retry recovers → guess contamination; neither recovers → guess ceiling). This is deliberately never invoked during dataset generation — the dataset's ground truth always comes from the known, deliberate injection (Step 4) and its verification (this step), never from a heuristic's guess. It exists purely as a separate, non-learned comparison baseline for later evaluation.

## Step 7 — Choose and migrate the inference backend

Three backends were supported, used at different points in the project:

1. **MLX** (`mlx_lm`, Apple Silicon) — used for local development and the original small-scale validation study, no GPU server needed.
2. **Ollama** — a local/cloud server option, used briefly during early development.
3. **vLLM**, the backend actually used for all bulk dataset generation — chosen specifically because its `llm.chat()` method accepts a **list** of conversations plus a matching list of sampling parameters in one call, enabling genuine cross-trial batching (see Step 9) rather than one sequential API call per sample.

**Model**: `Qwen/Qwen2.5-7B-Instruct-AWQ` — 4-bit AWQ quantization, `float16` compute dtype. This specific choice was forced by hardware: the originally-planned MXFP4-quantized model cannot run on the free-tier Kaggle/Lightning T4 GPUs actually available (T4 is compute-capability 7.5 / "Turing," and MXFP4 requires Hopper/Ada-class hardware). AWQ 4-bit quantization fits comfortably in a T4's 16GB VRAM with headroom left over for the KV-cache batching needs of Step 9. `float16` (not `bfloat16`) is used because Turing-generation GPUs lack native bf16 tensor cores.

## Step 8 — Build the actual batched generation script

**File**: `btp-pipeline/scripts/run_study_vllm.py`. This is the script that ran the real, large-scale generation. It reuses every piece of logic from Steps 1–6 unchanged (topology validation, fault injection, uncertainty computation, baseline verification) — the **only** thing it does differently is *how* generation calls are dispatched, for GPU throughput.

### 8.1 Two-phase batching per topology

**Phase 1 — control trials**: every question's clean-control trial is run as one batch (or several, chunked by `--batch-size`) — for each node in topological order, one single `llm.chat()` call handles *every* pending question's prompt for that node simultaneously, rather than one call per question. This establishes every question's baseline (Step 5) before any fault trial for that topology begins.

**Phase 2 — fault trials**: every fault trial's injection is **resolved first** (fault content computed, validity checked, invalid ones logged as skips — see Step 4.4) for the *entire* topology, before any generation happens. Only then are all the resulting valid trial specifications run through the same per-node batched execution as Phase 1, each one verified against its own question's Phase 1 baseline as it completes.

### 8.2 How one batched node-execution actually works

For a given node and a batch of N pending trial specifications:
1. Build that node's exact prompt for each of the N trials individually (each trial may have different upstream context depending on what its earlier nodes produced, and a fault-injected trial gets its corrupted input/instruction substituted in here).
2. If this node is the fault's specific target in a given trial, that **one** trial's temperature is set to the noise temperature (Step 4.1) — every other trial in the same batch keeps normal temperature. This per-trial temperature isolation was explicitly checked (not just assumed) to make sure a batched noise fault doesn't accidentally leak elevated temperature onto neighboring trials in the same batch.
3. Send all N prompts to vLLM in **one single `llm.chat()` call**, each with `SamplingParams(temperature=..., max_tokens=..., n=k)` — vLLM natively supports both "many different prompts at once" and "k samples per prompt" in the same call, which is the real throughput win: k×N samples generated in roughly the time of one forward pass over the batch, not k×N sequential calls.
4. Compute each trial's uncertainty score for this node from its own k returned samples (Step 3's formulas, applied identically regardless of how the raw text was produced).
5. Feed each trial's result forward as input to its own downstream nodes in the next round.

### 8.3 Fault-grid coverage strategy

For each topology, the full theoretical fault grid is "1 clean control + (3 fault types × N nodes in the topology)" — e.g. 10 conditions for a 3-node topology, 19 for a 6-node one. Running every condition on every topology for every question would explode combinatorially, so:
- The **3 smallest topologies** (fewest nodes) get the **full grid** — every fault type on every node.
- The remaining **17 topologies** get **partial coverage**: control + at least one fault type per node, cycling `noise → contamination → ceiling` by the node's position in the topology, rather than the full cross-product.
- **Coverage-gap fallback**: if a node's cyclically-assigned fault type fails injection for *every* question in a topology (this happened for one specific node in two topologies — see Step 10), the script automatically retries with the *next* fault type in the cycle for that node specifically, rather than leaving that node with zero fault-trial coverage at all.

This trades exhaustive per-topology coverage for broader structural diversity across the whole 20-topology pool, within a realistic compute budget on free-tier GPUs.

### 8.4 Resumability

`--resume` skips any topology that already has complete records in the target log file, at **topology-level granularity** — a killed or crashed run, when relaunched with the same command, redoes at most the one topology that was mid-flight, never anything already completed. This was added specifically after a real multi-hour run had to be killed partway through with no other way to preserve its progress.

---

## Step 9 — Log every trial (and every skip) honestly

Two output files, both append-only, flushed to disk after every single trial (so a mid-run crash loses at most one in-progress trial):

- **`dataset/trials.jsonl`** — one JSON object per successfully-generated trial: the question, `true_label`, `fault_config`, `topology_id`, per-node uncertainty dicts (lexical/semantic/jaccard), the `verification` z-score result, the raw k samples per node, and (from later enrichment passes) additional derived fields.
- **`dataset/skipped.jsonl`** — one JSON object per trial that was *attempted* but whose fault injection turned out to be invalid (Step 4.4's `None`-return cases) — always logged with a specific machine-readable reason string, **never silently dropped**.

## Step 10 — Run it at scale, on free-tier cloud GPUs

Generation ran on **Kaggle** (free T4 GPU, ~30 GPU-hours/week per account, kernel-based workflow) and, in parallel on a **genuinely disjoint question set**, **Lightning AI** (Studios + Jobs, free-tier T4), to roughly double effective throughput without waiting on either platform's individual quota. This involved a substantial set of concrete operational practices — code-delivery patterns, log-streaming setup, a real NumPy version-conflict fix, GPU-queue management, and more — documented in exhaustive step-by-step detail in `docs/information.md` §3.6, not repeated here to keep this document focused on the data-generation logic itself.

## Step 11 — Find and fix real bugs (via reading actual content, not just checking that it ran)

The single most important discipline applied during dataset preparation: **a generation run can complete with zero crashes and correct-looking record counts while still containing real correctness bugs** — these only surface when someone actually opens generated records and reads whether the labeled fault visibly changed the model's output. Three such bugs were found and fixed this way, in the fault-injection code specifically:

1. **Ceiling role-dispatch bug**: `inject_ceiling()` compared the node's *ID string* (`"retriever"`) instead of its *role* — so on any topology using custom node IDs (`retriever_a`, `n0_r`, etc.), ceiling faults silently failed to apply at all. Fixed by threading an explicit `role` parameter through the function and dispatching on role everywhere.
2. **Hardened instruction never actually applied**: the pipeline's prompt-builder computed the hardened (ceiling-faulted) instruction correctly, but then used the *original*, unmodified instruction in the final prompt string regardless — every downstream-targeted ceiling trial ran with **zero real effect** despite being logged as `"ceiling"`. Fixed by routing the selected instruction into the actual final prompt, verified with a dedicated 4-case unit test.
3. **Contamination self-substitution**: the distractor substitute bank could select the clean, correct value as its own "wrong" substitute, producing a no-op fault that looked like contamination but wasn't. Fixed by excluding the clean value from the bank before sampling (the trial is skipped, with a logged reason, if the bank becomes empty as a result).

All three were fixed together, and **the entire dataset was regenerated from scratch** afterward — not patched or merged in place — specifically so the final dataset is internally consistent (no mix of pre-fix and post-fix records). Fixing bugs #1 and #2 together alone increased ceiling-fault representation in the dataset from 20 to 103 records (5.15×), since ceiling faults now actually reached the model for the first time.

**Verification that the fix actually worked** was done by reading real output, not just re-checking record counts: post-fix, downstream ceiling trials show genuinely constrained answers (e.g. "American nationality.", "New York City" — 2–5 words, matching a "5 words maximum" hardened instruction) instead of the old, unconstrained full-sentence answers that had silently ignored the fault entirely.

**One known, deliberately-not-fixed limitation** carried into the final dataset: contamination on a node with *multiple* parents only corrupts the *first* parent's output — other parents feeding that same node stay clean. This doesn't produce a wrong label, just a weaker-than-ideal signal for those specific multi-parent contamination trials — flagged as an explicit caveat, not silently hidden.

## Step 12 — Post-generation verification pass

**File**: `btp-pipeline/scripts/verify_results.py`. Run on the final combined log before the dataset is ever trusted for training — recomputes record counts, label distributions, per-topology coverage, and basic structural sanity checks **directly from the raw file itself**, rather than trusting any prose summary written about it. This project has a demonstrated history (Step 11) of prose/summary claims not matching underlying data, so this step is treated as non-optional, run after every regeneration.

---

## Step 13 — Final, verified dataset

- **Trial records**: `dataset/trials.jsonl` — the fully verified, post-bug-fix dataset.
- **Skip records**: `dataset/skipped.jsonl` — every invalid injection attempt, with a reason.
- **Topology pool**: `dataset/topology_pool.json` — the 20 fixed topology definitions every trial is generated against.
- **Generation parameters used**: `k=5` self-consistency samples per node, default temperature `0.7`, noise-fault temperature `1.2`, `max_tokens=350` for Retriever/Writer, `max_tokens=600` for Reasoner (a larger budget to accommodate its chain-of-thought).
- **Known, accepted data-coverage gap**: in the `star` and `triple_retriever_fanin` topologies specifically, one node (`retriever_c`) is never once used as a fault target anywhere in the dataset — traced to the fault-cycling logic (Step 8.3) always landing that specific node on `ceiling`, which fails its mandatory survival-verification check (Step 4.4) for it every time, in every attempted question. Decision: not fixed or regenerated — this simply means that node is excluded from the set of valid "correct answers" when scoring a model on those two topologies specifically; it was never a possible correct answer to begin with, so a model never predicting it there is not a real failure.

## Step 14 — Same process, scaled further (later, separate effort)

The exact same 14 steps above were later re-run, unmodified in their underlying logic, to regenerate an expanded dataset at **k=10** self-consistency samples per node instead of k=5 (finer-grained uncertainty resolution: 11 discrete lexical-uncertainty levels instead of 6) — including the same multi-platform parallelization approach (multiple Kaggle accounts plus Lightning AI, on disjoint question slices) to handle the roughly doubled GPU cost per topology. This is a distinct, later phase of the project and is documented separately, not covered in further detail here.
