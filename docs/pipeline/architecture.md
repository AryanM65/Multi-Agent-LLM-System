# Pipeline Architecture — Technical Reference

> Deeper API-level reference for `src/`'s core library. For the research motivation and high-level picture, see the [root README](../../README.md). This doc covers: the topology engine, the three uncertainty metrics, the fault-injection taxonomy, and the invariants the codebase enforces throughout — the detail level needed to actually modify or extend the pipeline, not just run it.

---

## 1. Topology engine (`src/topology.py`)

The pipeline is not hardcoded to a 3-node chain. A `Topology` is a DAG of `NodeSpec` objects:

```python
NodeSpec(node_id: str, role: str, instruction: str)   # role: "retriever" | "reasoner" | "writer"
Topology(nodes: Dict[str, NodeSpec], edges: List[Tuple[str, str]], topology_id: str)
```

**Validation** (`validate_topology`, called on every `run_pipeline()` invocation):
1. All nodes have valid roles
2. All edge endpoints reference real node IDs
3. Role ordering is non-decreasing along every edge (`ROLE_RANK = {retriever: 0, reasoner: 1, writer: 2}`)
4. Graph is acyclic (Kahn's topological sort — raises on cycle)
5. No isolated nodes in multi-node topologies

**Graph utilities**: `topological_order(topo)`, `parents_of(topo, node_id)`, `children_of`, `source_nodes`, `sink_nodes`.

The 20-topology pool used for the actual dataset (`dataset/topology_pool.json`, 14 train + 6 OOD) is generated by `dataset/generate_topology_pool.py` — see [`docs/dataset/dataset_description.md`](../dataset/dataset_description.md) for the full schema.

## 2. Pipeline execution (`src/pipeline.py`)

```python
run_pipeline(topo, question, context, k, temperature, fault_config=None) -> PipelineTrace
```
Iterates `topological_order(topo)`, builds each node's prompt from its parents' outputs via `build_prompt()`, applies any active fault via `apply_fault_to_prompt()`, and calls `sample_node()`. `build_prompt()` also handles the fault-injection substitution hooks (`_corrupted_inputs` for contamination, `_hardened_instruction` for downstream ceiling faults) — see §4 below and `docs/model/model.md` Section 3 for the specific bugs found and fixed in this substitution logic.

## 3. Uncertainty metrics (`src/uncertainty.py`, `src/nodes.py`)

Every node is sampled **k times independently** at the same temperature. Three complementary metrics, all stored on `NodeResult` (never merged — see §6):

```
lexical_uncertainty  = 1 - (fraction of k samples matching the modal normalized answer)
semantic_uncertainty = entropy over embedding-cluster assignment of the k samples (Reasoner, Writer)
jaccard_uncertainty  = 1 - mean pairwise Jaccard overlap (Retriever, multi-item outputs only)
```

**Why semantic uncertainty exists**: the Reasoner writes free-form chain-of-thought, so even identical conclusions get phrased differently across samples — lexical matching alone gives a non-zero "baseline" uncertainty (~0.667 empirically) on clean data, which isn't itself a fault signal. Semantic clustering (via `all-MiniLM-L6-v2` embeddings, `sentence-transformers`) separates genuine disagreement from phrasing variance.

**Normalization** (`hotpotqa_normalize`): lowercase → strip punctuation → remove articles (a/an/the) → collapse whitespace — matches HotpotQA's own official SQuAD-style evaluation script.

## 4. Fault injection (`src/faults.py`)

All injectors are **role-aware** (dispatch on the node's `role`, not a string match against its `node_id` — a bug found and fixed specifically because non-chain topologies use custom node IDs like `retriever_a`, not the literal string `"retriever"`) and **reproducibly seeded**:
```python
make_rng(question_id, fault_type, target_node) -> random.Random
```
No injector calls the global `random` module — re-running any trial with the same `(question_id, fault_type, target_node)` produces byte-identical corrupted input.

| Fault | Mechanism | Recovery pattern |
|---|---|---|
| `noise` | Sampling temperature raised to `NOISE_TEMPERATURE` (1.2) at the targeted node only; input unchanged | Recovers on same-input retry at normal temperature |
| `contamination` | Targeted node's input replaced with a plausible-but-wrong distractor (Retriever: swapped gold paragraphs; Reasoner/Writer: parent's clean output replaced from a substitute bank, self-exclusion enforced) | Recovers on clean-input retry, not on same-input retry |
| `ceiling` | Targeted node's evidence stripped (Retriever) or instruction hardened to force information loss (Reasoner/Writer), with mandatory answer-survival verification before logging | Does not recover on either retry — genuine capability gap |

**Ceiling's mandatory verification**: `inject_ceiling()` returns `None` (never a silently mislabeled trial) if the gold answer string still survives in the stripped context — the caller must log this as a skip with an explicit reason, not drop it.

## 5. Diagnostic protocol (`src/diagnose.py`)

The retry-then-reprobe heuristic that *guesses* the fault type from uncertainty patterns alone (used as an evaluation/comparison baseline — **not** run during dataset generation, since the dataset's ground truth already comes from the known injection, not from this guess):

```
if uncertainty > threshold:
    1. Same-input retry (k samples, identical prompt) → recovers? -> "noise"
    2. Clean-input reprobe (k samples, known-good input) → recovers? -> "contamination"
    3. Neither -> "ceiling"
```
`retries=2` (not 1) for the same-input check — a single retry succeeding is weak evidence against a "soft ceiling" that intermittently recovers by chance.

## 6. Invariants enforced throughout the codebase

1. **Per-node uncertainties are never collapsed into a scalar.** `PipelineTrace.uncertainties()` always returns `Dict[str, float]`. This is the structural bet the entire project rests on — collapsing it would defeat the whole point of localizing *which* node failed, and is exactly what makes a graph-structured (GNN) downstream model the right fit (each topology node carries its own feature vector; see `docs/model/`).
2. **All model calls are sequential** within a single trial (no threading/asyncio) — though the vLLM-batched generation script (`run_study_vllm.py`) does batch *across* multiple trials' same-node calls in one `llm.chat()` call for GPU throughput; that's inter-trial batching, not intra-trial concurrency.
3. **Append-only, flush-per-record logging.** Every trial is written to its JSONL log immediately, `flush()`ed. A mid-run crash loses at most one in-progress trial.
4. **Skipped trials are always logged with a reason**, never silently dropped.
5. **A clean control trial always runs first per question**, establishing the baseline `verify_against_baseline` compares fault trials against.
6. **Every fault injector uses `make_rng`**, never the global `random` module.

## 7. Backend history

Ollama (`qwen2.5:7b-instruct-q4_K_M`) → MLX on Apple Silicon (`mlx-community/Qwen3-8B-4bit`, local dev) → vLLM serving `Qwen/Qwen2.5-7B-Instruct-AWQ` (dataset-scale generation on Kaggle/Lightning T4 GPUs — see [`docs/infra/kaggle-and-lightning-setup.md`](../infra/kaggle-and-lightning-setup.md)). The switch to vLLM was for genuine cross-trial batching (`llm.chat()` over lists of conversations); the switch to AWQ-quantized Qwen2.5 (from the originally-planned MXFP4 quantization) was because Kaggle/Lightning's free T4 GPUs (compute capability 7.5) cannot run MXFP4, which needs Hopper/Ada-class hardware.
